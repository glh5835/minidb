# MiniDB 设计文档 05：事务与崩溃恢复（WAL + 2PL + 死锁检测 + 恢复）

> 对应阶段 5 + steal/no-force 增强轮。代码：`minidb.wal.{WalLog, Recovery}`、`minidb.txn.{LockManager, TxnSession}`；事务协调在 `minidb.exec.Executor`。测试 36 项：LockManagerTest 11 + TxnIsolationTest 10 + RecoveryTest 11 + WalLogTest 4。

## 1. 总体协议：steal + no-force（简化 ARIES：redo + undo）

一句话：**任何脏页落盘前其 WAL 必已 fsync（日志临界区 + FlushHook 的 syncUpTo(pageLsn)）；commit 只 fsync 日志（no-force），数据页交给淘汰器（steal）；事务新建的页在提交时连同前驱页 mini-force（页创建与链改动不入日志）。**

- **WAL 先写原则的落地**：写路径的 {改页 → 追加 WAL → 回填 pageLsn} 在 BufferPool 的**日志临界区**内完成（他线程的淘汰挂起）；淘汰/flushPage/flushAll 三个写盘点统一经 FlushHook 把页 pageLsn 之前的日志强制落盘（`syncUpTo` 已 sync 则 no-op，靠 flushedLsn 高水位去重）。
- **`Page.pageLsn`**（阶段 1 预留的页头 [24..32)）：max 语义 + 写穿透，DML 追加日志后由 Executor 回填——预留字段在此获得真实消费者。
- **迁移式 UPDATE 记两条日志**：VarTable 迁移（update 返回新 RID）改记 `DELETE(旧RID)+INSERT(新RID)`，重放与撤销都以稳定 RID 为锚——顺带修复了"迁移行的恢复 undo 落空"的历史盲区。
- 性能效果：转账压测 20 线程 × 10 万次从 ≈110s 降到 **9.9s**（≈11×），小事务提交 ≈8,700 tx/s（fsync 关口径）。

## 2. WAL（WalLog.java）

### 记录格式（逻辑日志，整行镜像）

```
头 21B: [lsn:long][type:byte][txnId:long][payloadLen:int]
payload: [tableLen:short][table:UTF-8][pageId:int][slot:int][before:len+bytes][after:len+bytes]
镜像长度 -1 表示 NULL；行编码复用 RowCodec
```

六种类型：`BEGIN=1, INSERT=2, DELETE=3, UPDATE=4, COMMIT=5, ABORT=6`。INSERT 只带 after、DELETE 只带 before、UPDATE 强制两者（`append()` 校验，否则抛 `Code.WAL`）。LSN 单调递增 long 从 1 起。头内字节序统一大端（ByteBuffer 原生）；**长度字段必须顺序写入**——曾因绝对写 [17..21) 被随后从位置 17 开始的 writePayload 覆盖，导致 readAll 永远解析不出记录、恢复空转（详见踩坑总结第 16 条），由 `WalLogTest` 回归把守。

### 刷盘与截断

- `append()` 只写 OS 缓冲；`sync()` 才 `channel.force(true)`。
- **唯一强制点在 `Executor.commit()`**，顺序三步：① `wal.sync()`（DML 日志先落盘——WAL 先写原则）→ ② 逐页 `flushPage` + 系统页 → ③ append COMMIT + sync。
- `fsyncEnabled` 开关（`volatile`）：关闭后仅**进程崩溃**安全（OS 缓冲仍在），**断电**不保证——用于压测/批量导入提速。分级持久性是诚实的设计：断电安全由恢复测试单独验证。
- 打开日志时逐条校验完整记录恢复 lsn，遇半条/负长度 `truncate(pos)`——**天然容忍尾部截断**，这是断电模拟能成立的前提。
- checkpoint 简化为 `truncate()`（清空日志、lsn 重置 1），只在恢复完成后与正常 close 时调用。DDL 不走 WAL，直接 `engine.flush()`（DDL 无事务性，文档 07 有反思）。

## 3. 并发控制（LockManager + TxnSession）

- **粒度**：行级 RID 锁，key 为 `"table/pageId/slot"` 字符串。无表锁、无意向锁（单粒度）。
- **模式**：仅 `S/X`。`canGrant()`：空可授予；唯一 holder 是自己 → **锁升级**（S→X 放行）；S+S 兼容；其余拒绝。
- **数据结构**：`Map<String, LockEntry>`，`LockEntry{Set<Long> holders, Mode, Deque<Waiter>}` FIFO 等待队列。等待者 `wait(5)` 毫秒轮询 granted 标志，总上限 60 秒抛 `Code.DEADLOCK`（兜底超时，防等待图漏检的极端情况）。
- **释放**：集中在 commit/rollback 的 `releaseAll`——写锁严格 2PL 持有到事务结束。两个语句级例外：① RC 读 `LockExec.next()` 读完即放；② UPDATE/DELETE 扫描中"本次新获取且未命中 WHERE"的锁立即释放（不锁不相关的行）。

### 死锁检测（等待图）

- **每次 `acquire()` 入队后实时重建等待图**：遍历全部 LockEntry，对每个排队 waiter 加边 waiter→该锁全部 holders，再从**当前请求者** DFS 找环。不增量维护——注释明说：宁可每次 O(锁表) 重建，也不冒陈旧边漏检的风险。
- **牺牲者固定为请求者**（自己入队才可能成环，选它必然破环），检测到环先把自己移出队列再抛 `MiniDbException(Code.DEADLOCK)`。无启发式 youngest/least-work。
- **上层不自动重试**：调用方 catch DEADLOCK/LOCK → rollback → 重试（上限 200 次）+ `Thread.sleep(random)` 随机退避防活锁。压测显示重试是常态（10 万次转账重试 1.2 万~17 万次量级，零死锁最终失败）。

### 隔离级别（无 MVCC，纯 2PL 变体）

一个教学上诚实的选择：**读也用 X 锁实现**（注释原话"给扫描到的行加 S 语义行锁（实现用 X 锁 + RC 立即放/RR 持有）"），省掉 S/X 双模式授予逻辑。

- **READ COMMITTED**（autocommit 单语句默认）：读锁读完即放；未提交的他人写使读**阻塞**而非脏读（测试 `uncommittedChangesInvisibleToOthers` 断言读者被阻塞）；同事务内两次读可见他人新提交值（`readCommittedReadsLatestCommitted`）。
- **REPEATABLE READ**（显式事务默认）：所有锁持有到 commit（严格 2PL），读者重读保持旧值（`repeatableReadHoldsSnapshotValue`）。代价：**读读不并发、读阻塞写**。

## 4. 崩溃恢复（Recovery.java + Database.open）

```
Database.open() → wal.readAll()（容忍尾截断）
  → 日志非空则 Recovery.recover(db, records)：
      ① 分析：按 txnId 分组，收集已提交事务
      ② redo：LSN 序条件幂等重放全部 DML（含未提交——undo 随后撤销）
         INSERT: !rowExists → restoreAt+索引回插 / DELETE: 行==before → 再删
         UPDATE: 行==before → 改 after+索引
      ③ undo：未提交事务按 LSN 逆序条件撤销（镜像一致才动手）
  → wal.truncate()（checkpoint）→ engine.flush()
```

> **恢复真正干活的场景**：no-steal 下未提交脏页本不该落盘，但 DDL 的 `engine.flush()` 是 flushAll（无视 pin），会把未提交脏页一并写盘——此时崩溃后唯一能救原子性的就是 WAL 条件 undo（`ddlFlushedUncommittedDmlUndoneByRecovery` 专门验证：未提交的 555 被撤销回 100）。

两遍扫描（不是 ARIES 三阶段）：

1. **分账**：INSERT/DELETE/UPDATE 按 txnId 分组；收集有 COMMIT 记录的事务号（committed 集合）。
2. **条件 undo**：对每个**无 COMMIT** 的事务按记录**逆序**执行：
   - INSERT → 当前行 == after 镜像才 `delete(rid)` + 索引回删；
   - DELETE → 行不存在才 `restoreAt(rid, before)` + 索引回插；
   - UPDATE → 当前行 == after 才改回 before，并同步全部 B+ 树索引；
   - 表已删则忽略该记录。

   每步都**先比对镜像再动手**（幂等），因此恢复可安全重入——`recoveryIdempotentAcrossReopens` 专门验证连续两次重开结果一致。`redoCommitted()` 保留接口（force-at-commit 下通常空操作），是协议演进的三岔口。

运行时回滚走内存 undo 栈：`rollback()` 逆序执行 `undoActions`（Runnable 列表，含索引回补）→ append ABORT → 放锁 → `unpinAll(true)`。

## 5. 断电模拟（RecoveryTest.randomTruncationKeepsAtomicity）

方法论比"全文件随机破坏"更贴近真实：

1. 造 20 个已提交事务 + 1 个未提交事务，记录 `safe = wal.size()`（**safe 之前的字节必已 fsync 在盘**）；
2. `Database.crash()` = wal.close + `engine.abruptClose()`（**缓冲池不刷盘、日志不截断**）；
3. 用固定种子 `Random(2026)` 在 `[safe, size]` 随机 `truncate(cut)` 模拟 OS 缓冲丢失（允许切在安全线附近，即最多丢边界上 1 个事务）；
4. 断言：行数 ∈ [18,20]（容差 2）、每行值完整（原子性——不存在改了一半的行）、未提交事务的行全部不存在。

## 6. 转账压测（守恒验证）

`transfers20Threads100kConserveTotal`（@Timeout 120s）：

- 100 账户 × 初始 10000 = **总额 1,000,000**；**20 线程 × 5000 次 = 100,000 笔转账**；
- RC 隔离、`fsyncEnabled=false`（断电持久性由恢复测试兜底）、缓冲池 4096 页；
- DEADLOCK/LOCK → rollback 重试（上限 200）+ 随机退避；
- **断言：结束后 `SELECT bal FROM accounts` 求和 == 1,000,000**；
- 耗时：no-steal/force 时代 ≈110s → steal/no-force 后 **9.9s**（≈11×，来自 commit 不再逐页刷盘）。

另有 4 线程 × 50 次的小规模守恒测试在 TxnIsolationTest。协议专项测试：
`stealEvictedUncommittedPageNotVisibleAfterCrash`（8 页小池强制淘汰未提交页 → 断电 → 行不可见）、
`noForceCommitRecoveredByRedo`（commit 不刷页 → 断电 → redo 重建）、
`migratedUpdateUndoneAndRedoneCorrectly`（迁移 UPDATE 双向验证）。

## 7. 取舍与教训

| 决策 | 收益 | 代价 |
|------|------|------|
| steal + no-force（简化 ARIES） | commit 只 fsync 日志（转账压测 ≈11×）；缓冲池不再被事务 pin 占用 | 恢复 = redo + undo 两遍条件重放；FlushHook/pageLsn/日志临界区三件套保证先写 |
| 逻辑条件重放（非 physiological） | 走 Table API，与页布局解耦 | 大事务恢复慢；pageLsn 仅作 FlushHook 下界，不比较重放 |
| 读锁用 X 实现 | 单模式授予逻辑，代码减半 | 读读不并发、读阻塞写，吞吐受损 |
| 等待图实时重建 | 无陈旧边漏检 | 每次 acquire O(锁表) |
| 牺牲者固定请求者 | 破环必然成立 | 无 youngest/最少工作启发式 |
| fsync 可关 | 压测 10 万次转账 110 秒内完成 | 关闭后仅进程崩溃安全 |
| DDL 不入 WAL | DDL 直接刷盘最简单 | DDL 无事务性、无崩溃保护（踩坑总结有反思） |
