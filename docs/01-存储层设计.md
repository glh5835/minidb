# MiniDB 设计文档 01：存储层

> 对应阶段 1。代码：`minidb.common`（Rid/Bytes/异常）、`minidb.storage`（Page/DiskManager/StorageEngine/BufferPool/BaseTable/FixedTable/VarTable/RowCodec/Catalog/Database）、`minidb.repl`。约 2200 行，112 项测试。

## 1. 分层与职责

```
Database / Catalog          表与 schema 的目录管理（元数据持久化）
     │
Table 抽象（BaseTable）      定长 FixedTable / 变长 VarTable，行级增删改查
     │
BufferPool                   LRU + 脏页 + 引用计数（pin），一切页访问的必经之路
     │
StorageEngine                页分配/回收 + 空闲空间位图（链式目录页）
     │
DiskManager                  页粒度随机读写（文件 = 页的线性序列）

Rid(pageId, slot)            行标识，全库通用的行句柄
```

设计原则：**上层永远不直接碰文件**。B+ 树（阶段 2）、WAL 恢复（阶段 5）都只通过 BufferPool 拿页，这使脏页管理、崩溃语义有唯一的收口。

## 2. 页与磁盘

- **Page**：固定 `Page.SIZE = 4096` 字节，包装 `byte[4096]` + 元信息（`dirty`、`pinCount`、`pageLsn`）。`pageLsn` 字段从第一天就预留（页头偏移 [24..32)），是阶段 5 WAL 的伏笔——虽然最终协议没有用上它（见文档 05），但"页头给未来留位"避免了后期改页格式。
- **DiskManager**：`readPage(pid, buf)` / `writePage(pid, buf)`，页号即文件偏移 `pid * 4096`。文件头两页固定为系统页：
  - 页 0：全局元数据（总页数、位图链头等）；
  - 页 1：空闲空间位图目录的起点。

## 3. 页分配与空闲空间位图

- 每个位图页用 bit 数组标记"数据页是否空闲"，**每页覆盖 32736 个页号**；位图页自身用链表串联，分配位图页时存在自举问题（新位图页要标记自己）。
- `allocatePage()`：沿位图链找第一个 free bit → 置 1 → 若链上全部用满则追加新位图页。
- `freePage(pid)`：清 bit，并把页内容**磁盘清零**后归还——防止旧数据经"已删页"泄漏，也让"分配即零页"这一假设成立（B+ 树新节点无需显式初始化）。
- 故障注入点：位图链跨页、目录页溢出、坏页类型字节都有专门测试。

## 4. BufferPool（缓冲池）

- 数据结构：`LinkedHashMap(accessOrder=true)` 实现 **LRU 近似**（get 即触发访问序调整），容量可配（压测用 4096 页 / 16MB，正确性测试常用 8 页小池制造淘汰压力）。
- **引用计数防淘汰**：`pin(pid)` 使 `pinCount++`，淘汰器跳过 `pinCount > 0` 的页；`unpin(pid, dirty)` 归还并合并脏标记。全部页被 pin 时抛 `BUFFER_FULL`——这个"故障"是特性：阶段 5 的事务正好靠 pin 住未提交的修改页实现 no-steal（见文档 05）。
- **脏页写回**：`flushPage(pid)` 单页写盘（WAL 的 FlushHook 挂点）；`flushAll()` 全池刷盘。
- 统计接口：命中率、淘汰数、写回数——PERF.md 的数字都来自它。

**踩坑（详见踩坑总结）**：LRU + accessOrder 在"扫描大表挤掉热点索引页"上表现很差，教学实现未做 LRU-K/分区，但把池大小留成参数，压测时量化了差距。

## 5. 表抽象：定长与变长

### 5.1 RowCodec（行编解码）

小端字节序。变长列（VARCHAR）以 `[len int][bytes]` 前缀编码，定长列按宽度平铺；NULL 以长度 -1 表示（INT 列不接受 NULL——由 `Objects.requireNonNull` 强制，JDBC 层翻译成 SQLException）。编码入口 `RowCodec.encode(cols, values)`，解码 `decode(page, offset, cols)`。

### 5.2 FixedTable（定长记录）

- 页布局：**头部槽位数组 + 页尾占用位图**，记录体按定长槽紧密排列，原地更新，**RID 永不变化**。
- 删除 = 清位图 bit；插入优先复用空闲槽（首个 free bit），否则扩展到新页。
- 适用：INT/BIGINT/DOUBLE 等定宽列。UPDATE 原地覆盖，无碎片。

### 5.3 VarTable（变长记录，slotted page）

- 页布局：**槽位数组自上而下增长、记录数据自下而上增长**，中间为自由空间。
- 空槽组织成页内空闲链；每页维护空洞统计。
- **页内压缩**：自由空间不足但逻辑上有洞时，把记录向页尾紧凑搬移（**槽号不变**，RID 稳定）。
- UPDATE 放不下原页时**迁移到其他页并返回新 RID**——这是全库唯一使 RID 失效的操作，上层（索引）必须同步更新；`BaseTable.update()` 的返回值约定就是为此设计。
- 同表数据页用**双向链表**串联（页头存 prev/next），全表扫描不必经过目录；整页空时自动归还 StorageEngine。

### 5.4 为什么两种表都做

定长表是"教科书最小实现"，变长表逼出了 slotted page、空闲链、压缩、迁移这些真实数据库的核心问题。10 万行验证（`Phase1LargeDataTest`）对两种表各跑一遍插入→全量读回→逐字段比对。

## 6. Catalog 与 Database

- **Catalog**：目录页链持久化每张表的 schema（列名/类型/宽度）、firstPage、索引元数据；表多时目录页溢出成链。
- **Database**：门面类，`open(path)` 打开（或建库）、建表/删表、按名取 Table、createIndex/dropIndex（阶段 2）；阶段 5 后 `open()` 末尾挂接崩溃恢复。

## 7. REPL（阶段 1 形态）

读一行执行一行（`System.in` → 分发 → 打印 Result）。阶段 1 没有解析器，命令是 `.open/.create/.insert/.scan/.get/.delete/.update/.count/.pages/.stats`，查询计划**手工构造**（`SeqScanOp` 火山算子直连 Table.scan()）。阶段 3 后 REPL 增加 SQL 模式，手工命令保留作为存储层白盒调试入口。

## 8. 测试与验证

- 模块测试 112 项：字节编解码边界（负数/最大值/空串）、磁盘 IO 故障注入、LRU/pin/脏页语义、位图跨页、定长/变长表边界（VARCHAR 超长拒绝、空洞压缩、页回收）、目录溢出、REPL 全命令。
- 大数据验证：定长/变长各 **10 万条**插入后全量读回逐字段比对一致。
- 性能（PERF.md）：Table API 插入 194 万行/秒，全表扫描 2941 万行/秒。

## 9. 取舍与已知限制

| 决策 | 理由 | 代价 |
|------|------|------|
| 4KB 固定页 | 对齐 OS 页，B+ 树/位图/槽页都以它为单位 | 大 VARCHAR 跨页存储未支持 |
| LRU 单链 | 实现最小，统计齐全 | 扫描污染；无 LRU-K |
| 位图而非空闲链表 | O(1) 定位 free 页，结构可校验 | 回收页必须清零（多一次 IO） |
| 变长迁移换 RID | slotted page 标准做法 | 上层索引需感知 RID 变化 |
| 无多文件/表空间 | 教学聚焦 | 单文件即库 |
