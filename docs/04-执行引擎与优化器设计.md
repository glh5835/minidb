# MiniDB 设计文档 04：执行引擎与优化器（火山模型）

> 对应阶段 3 后半。代码：`minidb.exec.{ExecOp, Operators, AggregateExec, Expressions, Executor, LockExec, OneRowExec, SeqScanOp/Op}`，核心约 2900 行（Executor.java 含优化器约 1460 行）。测试：ExecutorSqlTest 50 + OptimizerTest 7 + 阶段 4 的 200 条端到端脚本（SqlE2eTest）。

## 1. 火山模型：open / next / close

每个算子实现 `ExecOp`：

```java
interface ExecOp {
    void open();
    Object[] next();      // null 表示流结束
    void close();
    List<String> columns();
    List<ExecOp> children();
    String describe();
}
```

一行数据是 `Object[]`（Integer/Long/Double/String/Boolean/null）。**流式算子**逐行拉取；**物化算子**在 open 时拉全（Sort/Distinct/GroupBy）。物化算子 close 不清缓存、重开复用——这不是偷懒：相关子查询每行重放子计划（§5），SortExec 的缓存正好把重复排序变成一次。

### 算子清单

| 算子 | 流式/物化 | 职责要点 |
|------|-----------|----------|
| `ScanExec` | 流式 | `table.scan()` 迭代，`currentRid()` 供写路径定位 |
| `IndexScanExec` | 流式 | B+ 树 rangeScan → 取 RID → `table.get(rid)`；捕获失效 RID 跳过（索引滞后防御） |
| `FilterExec` | 流式 | 循环 next 直到谓词真 |
| `ProjectExec` | 流式 | 逐列求值，支持 `*` 展开与别名 |
| `NestedLoopJoinExec` | 流式 | INNER/LEFT；`on==null` 即笛卡尔积；换左行时 `right.close(); right.open()` 重开右子树 |
| `SortExec` | 物化 | 全拉排序，NULL 最前，缓存复用 |
| `LimitExec` | 流式 | 先跳 offset 再计数 |
| `DistinctExec` | 物化 | `Set<List<Object>>` 整行去重，保持首现顺序 |
| `GroupByExec` | 物化 | 哈希聚合（§3） |
| `OneRowExec` | 单行 | 无 FROM 的常量表达式 |
| `LockExec` | 流式包装 | 包在叶扫描外，逐行加锁（文档 05） |

历史注脚：`Op`/`SeqScanOp` 是阶段 1 的雏形接口（返回 Row），阶段 3 换成 `ExecOp`（返回 `Object[]`、带元信息）后保留——REPL 的手工计划仍走旧接口，作为存储层白盒入口。两套接口并存是六阶段渐进开发的真实痕迹。

## 2. 表达式：计划期编译（Expressions.java）

- **绑定**：`bind(Ast.Expr, scope, Binder)` 在计划期把 AST 编译为 `EvalNode`（`Object eval(Object[] row)` 闭包）。列名解析**只做一次**，运行期按预解析下标 `row[idx]` 取值——避免逐行字符串匹配。
- **Binder 两个钩子**：`bindSubquery`（InQuery/Exists/ScalarQuery 三种子查询，§5）与 `lookupOuter`（相关子查询沿 `ctxStack` 逆序找外层列，支持多层嵌套）。`Executor implements Expressions.Binder`——执行器本身就是子查询的解析器。
- 列解析规则：限定列 `t.col` 先精确/忽略大小写匹配 scope；裸列去掉前缀逐个比对，命中多个抛"列名有歧义"。
- **类型系统**：运行期五类值。`compare()` 数值跨类型（任一 Double 按 double，否则 long）、字符串字典序、Boolean 可比；`arith()` int/long/double 提升，结果在 int 范围内收窄 Integer；**整数除法**、**除零/模零 → NULL**；NULL 参与比较一律 false、算术为 NULL（三值逻辑的简化：不区分 UNKNOWN）。
- **常量折叠**：纯常量子树（仅 Literal/BinOp/UnaryOp，无列引用/子查询）在绑定期求值一次成常量闭包——`WHERE 1/0 = 1` 不再逐行除零；LIKE 模式仍在绑定期一次性编译为正则。
- 存储层边界另有 `Executor.coerce()`：INSERT/UPDATE 时严格类型转换（DOUBLE 存 INT 列必须整值，超范围抛错）。

## 3. 聚合：哈希分组 + AST 改写

- `GroupByExec`：`LinkedHashMap<List<Object>, AggState[]>`，组键为分组列值列表，**LinkedHashMap 保持首组出现顺序**。open 一次拉全，输出行 `[组值..., 聚合值...]`，内部列名 `#g0..#gn, #a0..#am`。
- **AST 改写**（Executor.`planGroupTail/rewriteGroupExpr/substituteAlias`）：收集 SELECT/HAVING 中全部聚合到去重集合；把 HAVING/ORDER BY/投影里的组表达式替换为 `#gN`、聚合替换为 `#aN`、SELECT 别名递归展开。裸列既不在 GROUP BY 又不在聚合里 → 报错。
- **HAVING** = GroupBy 之上再包 FilterExec；管道固定为 `GroupBy → HAVING → Sort → Project → Distinct → Limit`。
- 无 GROUP BY：`globalGroup=true`，空输入仍输出一行（COUNT=0，SUM/AVG/MIN/MAX=null）。`AggState` 含 `longSum/doubleSum` 双轨，任一输入是 Double 即切 double；NULL 参数行跳过（COUNT(*) 除外）。

## 4. 子查询：物化 or 每行重放

`subqueryCorrelated()` 判定：列引用指向子查询 FROM 之外 → 相关。

- **非相关**：计划期**一次性物化**——`runSelect(stripOrderLimit(q))`（拷贝 AST 去掉 ORDER BY/LIMIT，因为它们不影响集合语义），IN 得 List 逐值比较，EXISTS 即 `rows.isEmpty()`，标量取首行首列、多行抛错。
- **相关**：`planWithOuter` 把 `OuterCtx`（外层列名 + row 槽位）压 `ctxStack` 后递归 planSelect；绑定后的 lambda 对每个外层行执行 `ctx.row = row; plan.open(); ... close()`——**嵌套循环式重放**。不做去关联（decorrelation），实现极简但复杂度 O(外层 × 子计划)；EXISTS 取到第一行即短路。
- 含子查询的连接谓词不参与重排，统一移入 `postPreds` 在 JOIN 后过滤（`containsSubquery` 递归检测）。

## 5. 极简代价优化器（内嵌 Executor，约 200 行）

没有独立 Planner 类——选择逻辑就在 `chooseScan / planJoinGreedy / planFromInOrder`。

**基数估算（数字全部显式可讲）**：
- `baseRows = max(1, 表行数)`；
- 等值谓词：`est = max(1, baseRows / 100)`；
- 范围谓词：`est = max(1, baseRows / 3^min(2, nBounds))`（每多一个界选择率 ÷3，封顶 9 倍）。

**索引选择**：谓词形如 `col op 字面量`（字面量可在任一侧）、列上**有索引**、列类型 INT/BIGINT——三条件齐备才考虑；**仅当 `est < baseRows × 0.5`（命中不到半表）才走索引**，否则 SeqScan 更便宜。同列多个 `>/<` 先**合并成一段闭开区间**（等值锚定双界），多候选列取 est 最小者；被索引覆盖的谓词从 Filter 中移除。

> 这次区间合并是 PERF.md 里最大的单点收益：合并前 `id>=a AND id<a+1000` 只用下界走索引，每次扫约 33 万索引项（73 ms）；合并后 0.222 ms/次（328×）。

**JOIN 顺序（纯 INNER 时贪心）**：首表取基数最小者；此后每轮 `cost = curSize × card(候选表) × sel`，候选表与已连接集合有连接谓词时 `sel=0.1` 否则 `1.0`，取 cost 最小者。连接谓词按 `takeJoinPredsBetween` 在对应连接处消费；**等值合取项（两侧均为裸列、分属连接两侧）拆为左右键选 HashJoin**（实测 2 万×5 千等值连接 ≈1900× 于纯 NLJ），其余做 residual，无等值键回落 NLJ。

**谓词下推**：WHERE/ON 合取拆分（`flattenAnd`）+ `soleTable` 判定单表谓词 → 下推到该表扫描之上。

**正确性优先的开关**：**只要出现 LEFT JOIN 就整体退回 `planFromInOrder` 按书写顺序连接、关闭一切下推**——右表谓词下推会改变 LEFT JOIN 语义（先过滤后连接 ≠ 先连接后过滤）。这是全代码库最典型的正确性/性能取舍。

**EXPLAIN**：`Executor.explain(sql)` 按 `describe()/children()` 缩进打印计划树；OptimizerTest 直接对 EXPLAIN 文本断言（7 项：等值走索引、范围走索引、无索引回退、谓词列无索引回退、小表在外层、大表过滤后顺序、SeqScan(small)）。

## 6. Executor 主入口

- `execute(String)`：BEGIN/COMMIT/ROLLBACK 维护 `activeSession`（默认 REPEATABLE_READ）；其余 `execute(stmt, TxnSession)` → `dispatch` switch 七种语句。
- 事务边界（无显式事务时）：语句级 autoCommit，RC 隔离；SELECT 只读不写事务日志；异常自动 rollback。
- **写路径**（trackInsert/runUpdate/runDelete）：行锁 → pinPage → WAL 物理日志（INSERT 记 after / UPDATE 记 before+after / DELETE 记 before）→ undo 闭包（含索引回补）。UPDATE 索引列值未变则不动索引。扫描经 `buildScanForWrite` 复用 `chooseScan`——**索引点更新只锁命中行**，不是全表加锁；两阶段：先逐行加锁收集命中 RID，再统一修改。
- `Result(columns, rows, message)`：查询返回列+行，DML/DDL 返回消息（JDBC 层从"N 行已插入"解析 updateCount——丑但诚实的层间约定）。

## 8. 取舍与未来工作

| 决策 | 理由 | 代价/未来 |
|------|------|-----------|
| Hash Join 仅处理等值合取项 | 等值是哈希的前提，非等值回落 NLJ | 纯非等值连接仍 O(n·m)；Merge Join 未做 |
| 相关子查询重放 | 避免 decorrelation 的正确性风险 | O(外层 × 子计划) |
| LEFT JOIN 关闭下推/重排 | 语义正确优先 | 混合 JOIN 查询拿不到重排收益（等值 LEFT 仍可用 HashJoin） |
| 哈希聚合全内存 | 简单、快 | 无 spill，超内存数据集失败 |
| VARCHAR 索引键 ≤255 字节 | 保住 B+ 树不变量 | 超长列建索引即拒绝 |
