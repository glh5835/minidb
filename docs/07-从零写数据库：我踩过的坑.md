# 从零写数据库：我踩过的坑

> MiniDB 六阶段开发复盘。每一条都是真实发生的：有的是红了测试才修的 bug，有的是压测数字逼出来的优化，有的是写完下一层才发现上一层埋的雷。按"现象 → 根因 → 修法 → 教训"记录，希望能让下一个从零写库的人少走几步。

## 坑 1：NPE 从存储层一路穿透到 JDBC 调用方

**现象**：阶段 6 收尾时 `JdbcTest.setNullProducesNull` 失败——期望 `SQLException`，实际收到裸 `NullPointerException`（消息还是中文的 "INT 列不接受 NULL"）。存储层用 `Objects.requireNonNull` 强制非空，这个 NPE 穿过 Executor、Statement，原样落到了用户代码里。

**修法**：`MiniDbStatement.execute` 的 catch 链补上 `RuntimeException` 分支，统一翻译成 `SQLException(msg, cause)`。

**教训**：**模块边界是异常的翻译点**。JDBC 契约要求一切失败以 SQLException 呈现；推而广之，每一层的对外 API 都应该有"异常守门员"，内部实现细节（哪怕是异常类型）不该泄漏。存储层用 NPE 表达约束在内部是清晰的，但没人替它翻译，它就成了 bug。

## 坑 2：测试里的受检异常，编译期才炸

**现象**：同一时期，`JdbcTest.acceptsOnlyMiniDbUrls` 编译失败——`d.connect(...)` 声明抛 `SQLException`，方法签名没写 `throws`。

**教训**：小事，但暴露了一个节奏问题——测试写完没有立刻编译就提交到了工作区，导致"阶段做到一半"的状态持续到了下一次会话。**测试也是代码，写完先编译再继续**，别攒。

## 坑 3：走了索引，反而要扫 33 万个索引项

**现象**：100 万行压测里，`WHERE id >= a AND id < a+1000` 走索引要 **73 ms/次**——明明是范围查，却比预想慢了两个数量级。EXPLAIN 一看：确实走了 B+ 树。

**根因**：优化器对同一列的多个比较谓词是逐个独立处理的，只把 `id >= a` 翻译成了树搜索下界，上界 `id < a+1000` 留给了 Filter。结果是定位到下界后**沿叶链扫到树尾**，再由 Filter 逐行拒绝。

**修法**：同列谓词先合并成一段闭开区间（等值锚定双界），上下界都交给 `rangeScan(from, fromInc, to, toInc)`。73 ms → **0.222 ms**（328×），每次只触碰约 5 个叶页。

**教训**：**"用了索引"和"用好索引"之间隔着区间合并**。教科书讲 B+ 树范围扫描时默认你只有一个区间，而真实 SQL 的 WHERE 是谓词集合——从集合到区间的归并是优化器的活，不做等于白建树。PERF.md 里这段对比成了全项目最有说服力的一个数字。

## 坑 4：谓词下推差点毁掉 LEFT JOIN 语义

**现象**：阶段 3 写谓词下推时很顺：拆 WHERE 合取、判单表、推到扫描上。直到写 `LEFT JOIN` 的测试——右表的过滤条件被推到连接**之前**执行，左连出来的"未匹配行"被提前过滤掉了，补 null 的行全没了。

**根因**：`右表谓词先过滤再左连` ≠ `先左连再过滤`。对 INNER 两者等价（下推安全），对 LEFT 不等价。

**修法**：只要 FROM 里出现 LEFT JOIN，整体退回**按书写顺序连接、关闭一切下推**，代码注释写明原因。

**教训**：**优化器的每条 rewrite 规则都要先问"在什么条件下等价"**，而不是"能不能更快"。等价性失效的场景（外连接、半连接、聚集、limit）比规则本身更值得写进注释。宁可慢，不可错——这也是教学实现和工程实现的分水岭应该画在哪的答案。

## 坑 5：UPDATE 不改索引列，也去删插索引

**现象**：阶段 5 并发测试里偶发"索引扫描漏行"——某事务明明插入了行，另一个事务走索引却查不到。

**根因**：UPDATE 无脑执行 `indexDelete(key) + indexInsert(key)`。即使索引列值没变，删插之间也存在一个**索引里没有该项的窗口**，并发走索引扫描的事务正好落进窗口就漏行。

**修法**：UPDATE 前比较索引列新旧值，**未变则完全不动索引**。

**教训**：**"先删后插"不是更新的原子替换**。凡是有中间状态的写法，在并发下都是 bug 温床。做并发正确性的意识要在写 DML 路径的第一天就有，而不是等隔离测试教会你。

## 坑 6：锁释放的"跳队"竞态

**现象**：LockManager 早期版本释放锁后只做 `notifyAll`，由等待者自由竞争——结果后来者可能抢在排队更久的 waiter 前面拿到锁（新请求直接发现锁空闲就拿了）。

**修法**：`release()` 时**直接把队首 waiter 授予进 holders**，notify 只是唤醒它确认事实；新请求者发现锁被占（哪怕旧的刚走）就老老实实排队。

**教训**：**唤醒 ≠ 授予**。把授予决定权留在锁管理器手里（谁拿锁是管理器说了算，等待者只是被通知"轮到你了"），FIFO 才真正成立。这个模式和 `synchronized` 的非公平语义正好相反，写的时候要想清楚自己要哪种。

## 坑 7：等待图的增量维护，漏检死锁

**现象**：最初想增量维护等待图（加边/删边事件驱动），既省 CPU 又显得高级。推演时发现：边删早了（事务刚拿到锁但还没清等待标记）、边加晚了，都可能让环在窗口期内不可见——**漏检死锁比多扫一遍图严重得多**，它会挂死线程直到 60 秒兜底超时。

**修法**：每次 `acquire()` 入队后**实时重建**整个等待图再从请求者 DFS。O(锁表) 的重复劳动换来"看见的图永远是真相"。

**教训**：**数据结构可以重建，正确性不能概率化**。死锁检测是低频路径（只在要排队时才跑），重建的代价完全付得起。把性能优化用在高频路径上，把正确性留给低频路径慢慢来——这个分工比反向划算。

## 坑 8：缓冲池"全部页被 pin 住就报错"，后来成了事务的地基

**现象**：阶段 1 的 BufferPool 遇到所有页都被 pin 时抛 `BUFFER_FULL`，当时当作故障注入点写进了测试。阶段 5 设计 no-steal 协议时发现：**"未提交事务的修改页不许落盘"正好就是"pin 住不许淘汰"**——白捡的机制，一行没改。

**教训**：**把资源耗尽做成显式异常而不是静默驱逐**，短期看是诚实的失败，长期看是在给未来的自己留接口。如果当初 BufferPool 遇到压力静默淘汰脏页，阶段 5 的崩溃一致性就无从谈起。

## 坑 9：pageLsn 留了位置，最后没用上

**现象**：阶段 1 给页头 [24..32) 预留了 pageLsn 字段，打算按 ARIES 风格做"页 LSN vs 日志 LSN"比较。阶段 5 最终选了 no-steal + force-at-commit：先写原则由 **commit 内部的操作顺序**（先 `wal.sync()` 再 `flushPage`）保证，页上的 LSN 没有任何写入点。

**教训**：这是"预设计"的正面教材还是反面教材？我倾向正面：留字段花了 8 个字节的页头，换来的是"将来改 steal 协议不用改页格式"。但也要诚实：**为未来留的机制如果一直不用，它就是无人测试的死代码**（幸好它只是个字段不是逻辑）。预留数据格式 ≠ 预留逻辑，前者廉价，后者昂贵。

## 坑 10：DML 走了 WAL，DDL 没走

**现象**：阶段 5 的 WAL 覆盖 INSERT/DELETE/UPDATE，但 CREATE/DROP TABLE 直接 `engine.flush()`，没有 BEGIN/COMMIT、没有崩溃保护。测试里"建表后崩溃"的组合是靠恢复流程里"表已删则忽略该记录"的防御性判断兜住的。

**教训**：**事务性要么覆盖全部写路径，要么明确声明哪些路径不在保护范围内**。半覆盖的 WAL 最危险的地方是给人一种"我有 WAL"的错觉。文档 05 把"DDL 无事务性"列为已知限制，比假装它安全诚实。

## 坑 11：updateCount 是从中文消息里正则出来的

**现象**：Executor 的 DML 返回 `Result.message = "3 行已更新"`，JDBC 层 `parseUpdateCount` 用正则 `(\\d+) 行` 从消息文本里抠出行数。改一下消息措辞（比如换成英文），JDBC 的 updateCount 就全变 0——而测试可能还绿着。

**根因**：阶段 3 定 Result 协议时只有 REPL 一个消费者，message 面向人类；阶段 6 让机器从人类文案里解析数据。

**教训**：**给人看的字符串和给机器看的结构体，从第一天就要分开**。`Result` 本可以加一个 `updateCount` 字段（数据已有，只是没放进结构）。层间协议里"顺手复用"的每一处，都会在下一层变成脆弱的隐式契约。

## 坑 12：压测计数器从没递增过，我却盯着它看了半天

**现象**：转账压测打印"死锁回滚 0 次，重试 12 万次"，一度以为死锁检测太神了。读代码发现 `deadlocks` 计数器**从未被递增**，永远打印 0——真实死锁全被记进了 retries。

**教训**：**没有观测值的指标是负资产**：它给出确定性的错误答案。修掉之前，任何基于它的判断都是自欺。压测输出先审指标本身，再看指标数值。

## 坑 13：回收页不清零，旧数据会"复活"

**现象**：阶段 1 设计页回收时，最初只想把位图 bit 清掉完事。推演 B+ 树场景：分配一个"新"页拿到的是旧叶的残留内容——键、指针、叶链全是上一个主人的，若新节点初始化不彻底，扫描会读出幽灵行。

**修法**：`freePage` 时**磁盘清零**后再归还，让"分配即零页"成为全库可依赖的不变量（B+ 树新节点因此无需显式初始化）。

**教训**：**回收资源时的清理义务要写进不变量**，不能指望每个使用者自觉。多花一次 IO 买下全库的初始化假设，这买卖划算。

## 坑 14：变长表 UPDATE 的 RID 漂移

**现象**：VarTable 的 slotted page 里记录放不下原页时要迁移，RID 随之改变。阶段 2 的索引 value 存的是 RID——如果 UPDATE 导致迁移而索引不知道，索引就指向虚空。

**修法**：`BaseTable.update()` 的返回值约定为"可能的新 RID"，上层（Executor）拿到后同步更新全部 B+ 树条目；页内**压缩搬移保持槽号不变**，把"RID 漂移"压缩到"迁移"这一个场景。

**教训**：**行的身份（RID）稳定是索引、锁、WAL 三家的共同地基**。定长表原地更新天然稳定；变长表做不到时，就要把"什么时候会变"收窄到最少场景并让所有持有者知情。身份语义越稳定，上层的公式越简单。

## 坑 15：仓库根目录长出了 demo.db.wal

**现象**：阶段 6 跑完 JdbcDemo，`git status` 里出现未跟踪的 `demo.db.wal`——`.gitignore` 只写了 `*.db`，漏了 WAL 副产品。

**修法**：`.gitignore` 补 `*.db.wal` / `*.wal`，顺手清掉工作区残留。

**教训**：**每个二进制副产品出现的第一天就该进 ignore**，否则它迟早混进某次 `git add -A`。数据库项目尤其如此：主文件、WAL、临时库，一个都不能少。

## 坑 16：WAL 写了一年，没人发现它读不出来（全场最痛的一坑）

**现象**：收尾阶段给 WalLog 补格式测试（记录往返、残缺尾部自愈），一跑就崩：`readAll()` 返回 **0 条记录**——不是重开后读不出，是**追加完立刻读都读不出**。而此前 7 个恢复测试全部绿灯。

**根因**：append 里长度字段用**绝对写** `putInt(buf, 17, len)`（不推进 position），紧接着 `writePayload` 从 position=17 **顺序写**载荷——前 4 个载荷字节把长度字段精确覆盖。于是盘上每条记录的"长度"都是载荷首字节的乱码：readAll 第一条记录就因 len 越界 break；WalLog 构造器的"尾部自愈"则把整个文件当残缺尾truncate 成 0。

**为什么 7 个恢复测试全绿——这才是真正的教训**：no-steal + force-at-commit 协议下，未提交脏页从未落盘、已提交数据页 commit 时已落盘，**正确性根本不依赖 WAL**——恢复流程空转（readAll 空 → 什么都不撤）结果也恰好正确。测试全部在验证"最终状态对"，没有任何一个**直接断言 WAL 能被读回**。直到 DDL 场景出现：`engine.flush()` 是 flushAll、无视 pin，未提交脏页借 DDL 落盘 → 断电 → 恢复空转 → **未提交的 555 幸存**，原子性真被破坏了。新回归测试 `ddlFlushedUncommittedDmlUndoneByRecovery` 在旧代码上必红（expected 100 but was 555），修复后通过——这才是 WAL 第一次真正"干活"。

**修法**：长度改为顺序 `buf.putInt(plen)`，顺带统一大端（此前头部长度是小端、其余字段大端的混合布局）；4 处读端同步；删掉自定义小端辅助方法防止回归。

**教训**（三条，一条比一条疼）：
1. **"写入函数"必须有对应的"读出测试"**。序列化代码没有 round-trip 测试，等于没有测试——它不会崩溃，只会静默地写垃圾。
2. **依赖"最终状态正确"的测试无法区分"机制生效"和"机制碰巧不需要"**。当协议让某个组件退化（这里是恢复空转），绿灯是假象。要给每个组件一个"只有它才能救场"的场景（这里是 DDL 刷盘 + 断电）。
3. 顺带发现 Recovery.java 里两行调试打印从未被察觉——因为恢复循环从未真正执行过。**死路径上的代码，连它的 println 都不会出卖它**。

## 坑 17：变长键布局，三轮调试各修出一个"我以为是那个"的 bug

**背景**：把 B+ 树从定长键改成变长键（目录 + 双端布局），冒烟对拍 TreeMap。三轮失败，每轮修掉的真 bug 都不是我第一眼认定的那个：

1. **三目运算符类型提升**：`lv == d ? lv : d`（long/Double 混合）结果类型被提升为 double，`Long 1` 永远不等于 `Double 1.0`——跨类型键归一全部失效。修法是独立 return。**教训：Java 三目在数值装箱类型上是个陷阱，比较语义的代码别用它。**
2. **整体搬移 vs 前段搬移**：`insertLeafEntry` 把整个值区下移一格——中位插入时 pos 之后的条目地址与目标天然重合，整体搬反而把它们错位一格。顺序插入（pos==nk）永远不触发，随机插入立刻乱序。**教训："把整块都搬了"看似最安全，其实覆盖了"本不该动"的内存。**
3. **删除不压实累积空隙**：最初删除只在数据区头部前移 4 字节（目录缩位），尾部不动——每删一个键留 4 字节空隙，`fits` 的空间核算不含空隙，累计数百次后键数据写穿值区。修法是插删都把数据区紧贴目录压实（物理序=逻辑序顺带成立）。**教训：空间核算和空间现实必须来自同一个不变量。**

外加两个自己挖的坑：新根只写了右孩子（`insertInternalEntry` 保留 pos 槽左孩子的语义对空页不成立，child(0) 指向 0 号页）；`loadInternal` 同样丢最左孩子。**教训：设计"复用现有原语"时，先写下该原语对边界输入（空页）的完整前后置条件。**

调试方法论收获：`verify()`（目录偏移严格递增 + 键长合法 + 数据区不越界）挂在每个原语尾部，配合"逐操作审计"（每次插删后全树校验），比打转储猜快得多——它把"什么时候坏的"精确到操作，而不是靠肉眼对比字节。

## 坑 18：no-steal 的绿灯，又一次掩盖了恢复空转

坑 16 里 WAL 读不出来、恢复空转、测试全绿——steal 改造时同样的事又演了一遍，只是方向相反：`Recovery.undoRec` 对"迁移式 UPDATE"用旧 RID 锚定，`rowMatches` 落空就跳过——**未提交的迁移行在恢复中幸存**。这个盲区在 no-steal 下暴露面极小（脏页根本不落盘），所以迁移测试全绿。直到写 steal 的迁移测试（`migratedUpdateUndoneAndRedoneCorrectly`）才炸出来。

**修法**：迁移 UPDATE 改记 DELETE(旧RID)+INSERT(新RID) 两条日志，undo 按 LSN 逆序"先撤 INSERT 再撤 DELETE"，每条都以稳定 RID 为锚，天然正确。

**教训**：和坑 16 同源——**每个恢复分支都需要一个"只有它才能救场"的测试**。协议改造（no-steal→steal）会改变每个分支的暴露面，绿灯必须重新挣一遍。

## 坑 19：crash() 里藏着一个 sync，断电测试测了个寂寞

`Database.crash()` 调 `wal.close()`，而 `WalLog.close()` 内部**先 sync 再关**——所谓"断电"其实把全部日志（含未提交事务的）都刷出去了。`randomTruncationKeepsAtomicity` 的 `safe` 线因此恒等于文件大小，"随机截断"从未真正随机过。steal 改造时一并修掉：新增 `abruptClose()`（不 sync 直接关），安全线改为 `flushedBytes()`（fsync 字节高水位）——这才是"OS 缓冲中的字节丢了"的真实语义。

**教训**：**测试辅助方法会静默改变被测语义**。`crash()` 这种名字上模拟故障的 API，实现里任何一个"顺手严谨"（close 前 sync）都会把故障测试变成安慰剂。审查故障注入代码时，先问"这条路径上有没有人替我做了太多"。

## 如果重来一次

1. **先定层间协议的数据结构，再写实现**。Result.message 坑（坑 11）的本质是阶段 3 没想过阶段 6。
2. **并发语义提前到 DML 设计日**。坑 5、6 都是"先写正确路径，并发问题留给事务阶段"的债。
3. **观察手段随功能一起交付**。计数器（坑 12）、统计接口、EXPLAIN——它们不是锦上添花，是后续每个阶段的地基。幸好树高/利用率/stats 接口在阶段 1、2 就埋了，PERF.md 的数字全靠它们。
